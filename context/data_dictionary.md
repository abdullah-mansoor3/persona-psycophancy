## 2. Processed files (data/processed/)

### `participant_splits.csv`
| Column | Meaning |
|---|---|
| `participant_id` | dataset `pid` (int) |
| `split` | `train` (1,440) / `validation` (309) / `test` (309) |
| `split_seed`, `split_version` | `42`, `v1` — reproducible; regenerate only via the pipeline script |

Stratified on the *joint Wave 4 labels* of both targets, so the four answer combinations
are proportionally represented in every split (see manifest `strata_counts_by_split`).

**Allocation:** XGBoost → train/validation/test exactly. Persona experiments → no final
evaluation on train; pilot/prompt development on validation; final evaluation on test.
Peer pool → **train participants only** (never validation/test).

### `persona_profiles.csv`
| Column | Meaning |
|---|---|
| `participant_id`, `split` | identifiers |
| `persona_text` | exact `wave1_3_persona_text` (~95,000 characters on average; token-count it with your own tokenizer before inference) |
| `profile_question_count` | answered Qualtrics question blocks in the persona JSON (mean 158, range 156–158) |
| `profile_missing_count` | answered blocks with empty answers (max 0) |

Verified: contains **no target questions or target answers** (phrase-level scan on all
2,058 profiles: 0 hits). Do not edit `persona_text`; if context is too long, apply a
*consistent, documented* compression method and keep this file as the ground truth.

### `target_questions.csv`
One row per documented Wave 4 item: the two selected core targets (`selected_for_core=true`)
plus audited non-selected candidates (QID291, QID9_21, QID287, QID288, QID289) with
`selection_notes`. Columns: `question_id`, `selected_for_core`, `selection_notes`,
`question_type`, `universal`, `options_json`, `question_text_canonical`, `n_participants`.

### `target_question_variants.csv` — REQUIRED for the persona experiment
One row per participant × target. Columns: `participant_id`, `question_id`,
`wave1_3_question_text`, `wave4_question_text`, `options_json`,
`wording_identical_across_waves`, split columns.

**Why this file exists:** `QID9_3`'s passage (product category, product, price) is
**randomized per participant** (434 distinct passages). The Wave 4 human answer is about
the *exact product the participant saw*, so a comparable LLM answer must show that same
passage. Verified: wording is identical between waves 1–3 and Wave 4 for every participant.
QID196 wording is constant (marble-tray question) but is still included for uniformity.

**Rule for Member 3:** for each test participant, take the question text from this file
(each participant's own row), never the canonical text from `target_questions.csv`.

### `human_answers.csv`
One row per participant × target: `wave1_3_answer` (earlier), `wave4_answer` (ground truth),
`split`, `is_complete`. String labels are kept verbatim; do not convert to 0/1 in this file.
Code mapping (1-based option position): QID196 → 1 = `the small tray`, 2 = `the large tray`;
QID9_3 → 1 = `Yes, I would purchase the product`, 2 = `No, I would not purchase the product`
(see manifest `answer_code_maps`).

Train-pool majority answers (from `wave1_3_answer`): QID196 → `the small tray`;
QID9_3 → `No, I would not purchase the product`.

### `peer_responses.csv`
One row per focal × question × peer (309 × 2 × 3 = 1,854 rows; 618 groups).
Columns: `focal_participant_id`, `peer_group_id` (`"<pid>_<QID>"`), `peer_position` (1–3),
`peer_participant_id`, `question_id`, `peer_answer`, `peer_role` (`majority`/`minority`),
`reused_for_conditions` (`"B,C"`).

Design (all validated): exactly 3 peers; 2 with the training majority answer + 1 with the
minority; all peers from `train`; focal never their own peer; **the same group must be
reused for conditions B and C** (same `peer_group_id`, same `peer_position` order).
Never expose `peer_participant_id`, `peer_role`, or split info to the LLM — only the
`peer_answer` strings as peer messages.

### `xgboost_features.csv`
One row per participant (2,058) × split + **all 760 earlier answer columns** from
`wave1_3_response_label.csv` plus `participant_id` and split columns. This is a
*label-level* (string) table; encoding/imputation happens at training time so that
encoders are fit on the training fold only.

- **Secondary feature set (LLM-comparable):** manifest `xgboost_features.profile_columns`
  (634 columns) — flattened columns of exactly the QIDs found in the persona JSON. Use
  only these for the profile-only XGBoost so it sees the same historical information as
  the LLM persona.
- **Expanded set:** additionally `expanded_extra_columns` (126 columns) — earlier answers
  to Wave-4-experiment QIDs not in the persona. Report separately; not an apples-to-apples
  comparison with the persona.
- **Multi-select option columns** (`MAVR`/`MAHR`, 84 columns, list in
  `binarized_multiselect_columns`): binarized to `"0"/"1"`; `0` = option *not selected*
  (this is not missing data).
- **Branch (between-condition) columns** (e.g. earlier QID163/QID164 arms): `NaN` means
  *not assigned to that arm*. Never impute as an answer; one-hot encode with an explicit
  `__NOT_ASSIGNED__` category.
- **Free-text columns** (56 profile + 6 expanded, list in
  `column_semantics.free_text` in the manifest): excluded from the initial numeric models.
- **Per-model exclusions** (manifest `model_feature_exclusions`): drop
  `["QID196", "QID9_3"]` columns when predicting QID196; drop `["QID9_3", "QID196"]`
  (default) or the whole `QID9_1..QID9_40` family (strict) when predicting QID9_3.
- **Leakage guard:** every feature column originates from the wave‑1–3 CSV; no Wave 4
  value ever enters this file. (Earlier answers to the target QIDs *do* exist here by
  design — that is how the persistence baseline and peer pool are built — hence the
  above per-model exclusions.)

### `xgboost_targets.csv`
One row per participant × target: `wave4_answer`, `wave4_answer_code` (XGBoost label),
`wave1_3_answer` / `wave1_3_answer_code` (persistence baseline: predicts the participant's
own earlier answer), `split`, split fields. Train on train, select on validation, report
once on test. Baselines to beat: (1) majority class, (2) persistence (`wave1_3_answer_code`).

## 3. Manifest (`data/preprocessing_manifest.json`)
Records: seed, split version + counts + strata table, target metadata (exact options,
wording variants), answer code maps, persona counters + leak-scan result, full feature
column-role/exclusion lists, peer design, column semantics, and SHA-256 checksums of all
processed files. If a teammate regenerates the files, checksums in git-review messages
can be compared.

## 4. Do / Don't summary
- Do regenerate everything with `build_processed_dataset.py`; never hand-edit processed CSVs.
- Do use the participant's own QID9_3 passage (from `target_question_variants.csv`).
- Do keep B and C peer messages byte-identical (use `peer_group_id` + `peer_position` order).
- Do fit all transformers on the training split only.
- Do not use validation/test participants as peers, features of the persona prompt, or
  anywhere in model fitting.
- Do not impute branch NaNs as answers; do not treat multiselect `0` as missing.
- Do not show `pid`, split, roles, peer IDs, or any metrics to the LLM.
